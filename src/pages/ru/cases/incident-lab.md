# Лаборатория Fault-Injection и Observability в Kubernetes

### 🛠️ Обзор инфраструктуры
Симуляционный стенд для воспроизведения узких мест производительности, деградации ресурсов и каскадных отказов в микросервисных архитектурах. Проект используется для отладки алертов Prometheus, дашбордов Grafana и проверки устойчивости сервисов под экстремальной нагрузкой.

- **Репозиторий исходного кода:** [incident-lab](https://github.com/ajdanoff/incident-lab)
- **Ключевой стек:** Kubernetes (cgroups) // Prometheus v2 // Grafana // k6 // Python ASGI

## 🏗️ Воспроизводимые паттерны отказов и метрики диагностики

Лаборатория изолирует характерные сигнатуры сбоев облачной инфраструктуры и фиксирует точные метрики для их локализации:

```text
               [ Искусственная нагрузка / Burst Traffic ]
                                   │
         ┌─────────────────────────┴─────────────────────────┐
         ▼                                                   ▼
[ Сценарий А: CPU Throttling ]             [ Сценарий Б: Reconnect Storm ]
├── Период CFS cgroups: 100 мс             ├── Таймауты на API Gateway
├── Симптом: скачок p95/p99 latency        ├── Симптом: рост HTTP 5xx и ретраев
└── Метрика: `container_cpu_cfs...`        └── Метрика: `api_inflight_requests`
```

### 1. Иллюзия свободного CPU при Kubernetes CPU Throttling
* **Проблема:** стандартные графики показывают среднюю утилизацию CPU на уровне 50–60%, в то время как `p95`/`p99` время ответа сервиса резко деградирует.
* **Причина на уровне ядра:** планировщик Linux CFS выделяет квоту CPU микроокнами по **100 мс**. При всплеске препроцессинга данных контейнер вырабатывает всю квоту за первые 20 мс, после чего `cgroups` принудительно замораживает потоки на оставшиеся 80 мс периода.
* **Ключевые метрики для алертинга:** отношение `container_cpu_cfs_throttled_periods_total` к `container_cpu_cfs_periods_total` и суммарное время заморозки `container_cpu_cfs_throttled_seconds_total`.

### 2. Каскадные таймауты и реконнект-штормы
* **Проблема:** локальная задержка в одном из нижестоящих сервисов валидации приводит к отказу всего API-шлюза.
* **Причина:** при превышении таймаутов клиенты и воркеры запускают агрессивные циклы повторных попыток (retry storm), мгновенно исчерпывая пул соединений с БД и брокером сообщений.
* **Ключевые метрики:** рост `api_inflight_requests` и всплеск ошибок `http_requests_total{status=~"5.."}`.

## 📈 Инженерные выводы для продакшена

* **Настройка SLO/Alerts:** мониторинг только среднего CPU создаёт слепую зону; критические алерты должны опираться на долю затроттленных CFS-периодов и хвосты распределения задержек (`p99`).
* **Защита от самоиндуцированного DDoS:** обязательное внедрение Circuit Breakers и экспоненциального backoff с джиттером на уровне межсервисных клиентов.
